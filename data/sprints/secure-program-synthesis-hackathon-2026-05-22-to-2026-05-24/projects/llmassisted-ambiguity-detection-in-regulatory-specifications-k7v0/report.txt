Abstract
Regulatory software often begins with natural-language requirements that are understandable to
humans but insufficiently precise for reliable implementation. This project studies that problem
using GST-style compliance rules involving filing dates, invoices, actors, penalties, and exceptions.
A lightweight Python pipeline was developed using three sequential LLM calls: requirement for-
malization, ambiguity auditing, and structured scoring. Using Google Gemini on seven GST re-
quirements, the pipeline identified recurring underspecification patterns including missing temporal
boundaries, undefined evidence requirements, unclear actor responsibilities, and incomplete excep-
tion handling.
The primary contribution is practical: an LLM-assisted review pass can help surface unresolved
implementation questions before formal methods or software engineering workflows begin. The
system is not intended as legal authority or proof infrastructure, but as a specification elicitation
aid for regulatory software development.
Keywords:LLMs, specification engineering, regulatory compliance, ambiguity detection, for-

1. Introduction
Formal verification and secure program synthesis depend on good specifications. In practice,
many systems do not start with precise specifications; they start with policy text, product
requirements, regulations, or informal domain-expert explanations. Dodds makes a similar
point in“Specifications Don’t Exist”[1]: for many useful systems, the hard part is not only
proving code correct, but deciding what the correct behavior should be.
This project applies that problem to GST/tax compliance rules. GST requirements are
written for accountants, lawyers, and businesses, not for software engineers. A rule such as
“late filing attracts a penalty of Rs. 50 per day” sounds precise, but software still needs to know
when the clock starts, whether there is a cap, which return is covered, and what happens in
exceptional cases.
The goal of this project is to build a lightweightambiguity finderfor regulatory require-
ments. It doesnotattempt to determine the correct legal answer. Instead, it identifies missing

2. Related Work
This project is closest to work on specification quality and AI-assisted formal methods. Dodds’
work [1] suggests the idea that the specification itself is often the bottleneck. The Vericoding
benchmark [2] studies the LLM generation of formally verified programs fromformalspecifi-
cations, which come later in the chain. This project focuses on whether the original human
requirement is specific enoughbeforeformalization.
Atlas Computing’s work on AI-assisted specification tools is also relevant [3]. Their specifi-
cation IDE explores how natural language can be mapped to formal specifications and reviewed
by humans. This project is more domain-specific: it does not build an IDE or generate proof
artifacts. It focuses on a practical first-pass check for regulatory software requirements.
The gap addressed here is the step between plain-English regulation and implementation:
finding the missing questionsthat developers should answer before writing code.

5. Discussion and Limitations
The results confirm that regulatory language has systematic ambiguity patterns. The project
is useful because these are exactly the questions developers face when converting compliance
rules into software. An LLM pipeline can act as asimple and cheap first-pass reviewer
before implementation begins.

Limitations
The main limitation is that model output is not ground truth. An LLM may flag false positives,
miss real legal issues, or hallucinate plausible-sounding but fictitious edge cases. The project
also uses a very limited sample of GST-style requirements rather than a labeled benchmark.
Outputs should be read asquestions for review, not as legal conclusions.
Future Work
The projected next steps are: (1) validate model-flagged ambiguities against expert-labeled
examples or real tax disputes, and increase the sample size; (2) extend to other compliance
domains such as KYC, payroll, insurance claims, or privacy policy enforcement; and (3) add
human review, source citations to legal sections, and multi-model comparison.
6. Conclusion
This project built a small, reproducible ambiguity finder for GST-style regulatory require-
ments. The pipeline formalizes a requirement, attacks the formalized version, and scores the
ambiguity as JSON. In the completed Gemini run, all seven analyzed requirements were rated
underspecified, with repeated issues around time, actors, evidence, and exceptions.
The main lesson is simple: regulatory requirements often need spec elicitation before im-
plementation. LLMs are not a substitute for legal review or formal proof, but they can help
surface missing questions early enough to be useful.

B. Limitations and Dual-Use Considerations
False positives are possible: the model may flag issues that a tax expert considers obvious from
statutory context. There is also no formal proof that the found ambiguities are real. The tool
could be misused to create confusion around compliance rules, so outputs should be presented
as questions for review rather than legal conclusions.
C. LLM Usage Statement
LLM assistance was used to help draft the project framing, code structure, and report format-
ting. The pipeline results inresults/output.jsonwere generated through Google Gemini
API calls where quota allowed. All claims in the report were reviewed against the generated
output and the local code.
