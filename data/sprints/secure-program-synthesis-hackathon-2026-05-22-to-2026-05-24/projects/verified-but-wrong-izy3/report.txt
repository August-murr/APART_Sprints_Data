Verified but Wrong: Auditing When Vericoding
 Verifies the Wrong Target
 
1. Introduction
Formal verification can tell us whether code satisfies a specification. Vericoding extends this into program synthesis: generate
candidate implementations, verify them against a formal target, and select code that passes.
But verification against a formal target does not prove that the target was the right one.
If the formal target omits an intent-critical requirement, then verification may certify a program that is correct relative to the written
spec and wrong relative to the user's intent. We call this outcome verified-but-wrong: an implementation passes the public formal
specification used for candidate selection, but fails the natural-language, policy, or product intent that the formal specification was
meant to capture.
Example. In DA0208, the natural-language task asks for the minimum uniform box size needed to pack cowbells. The reconstructed
public target only requires a nonnegative result. A candidate that always returns 0 verifies with Dafny reporting zero errors, but fails
intended examples expecting 5, 10, and 10. Adding the missing target constraint blocks the same bad candidate.
The claim is not that weak specifications exist. That is already known. The vericoding-specific failure is that weak specifications
become trusted selection targets. Verification can then amplify confidence in code that is only correct relative to an incomplete target.
Existing vericoding benchmarks primarily evaluate implementation validity against a supplied formal target. We evaluate target
validity itself: whether the supplied formal target preserves natural-language or policy intent before it is used for candidate selection.
Contributions.

The main contribution is not the gate. The main contribution is the missing evaluation layer: target validity before
implementation selection.
Scope of claims. This paper does not claim that verified-but-wrong failures are common across all vericoding benchmarks, nor that Dafny
verification is unsound. The narrow claim is that target-validity failures can occur when a formal public target omits requirements present in the
natural-language or policy intent, and that vericoding pipelines can amplify this failure by using the incomplete target for candidate selection. The
three direct-Dafny cases establish the strongest evidence for simple underconstraint classes, while the Tier 2 adapted demonstrations support
broader omission patterns such as missing simulation semantics, missing minimality, missing exact-value constraints, and related target gaps.
Abstract
Vericoding can prove that generated code satisfies a supplied formal specification, but not that the specification is
the right target. We study target validity: whether a formal target preserves natural-language or policy intent before
candidate selection. We audit a public Dafny vericoding benchmark snapshot with 2,334 records and 1,448 useful
natural-language descriptions. A scanner found 128 candidate target-validity gaps; adjudicating all 41
high-confidence candidates produced 11 verified-but-wrong demonstrations, including 3 direct-Dafny cases where
deliberately wrong implementations verify with zero errors and fail intended examples. Repaired targets block all
three Tier 1 cases. A controlled 12-task benchmark isolates the mechanism: naive specs produced 12/12
verified-but-wrong selections, checklist-critic specs 5/12, and oracle/full specs 0/12. These results are demonstration
evidence, not prevalence estimates. They motivate target-validity auditing before using formal specs for vericoding
selection.

2. Background and Failure Model
Vericoding benchmarks evaluate whether models can synthesize programs and proofs that satisfy formal specifications.
DafnyBench, FVAPPS, and the Vericoding benchmark all test whether generated artifacts verify against supplied formal targets.
This paper studies a complementary question. Instead of asking whether a model can satisfy a formal target, we ask whether the
formal target preserves the natural-language or policy intent it is supposed to represent.
The issue is related to specification validation, CEGIS, CEGAR, executable oracles, and spec-conditioned decoding. However, the
failure mode is different in a vericoding pipeline. In ordinary implementation debugging, an incomplete spec may cause missed bugs.
In vericoding, the incomplete spec can become the object of optimization and selection. A candidate can be selected because it
satisfies the wrong target.
Successful formal verification may also increase user trust. A program that is merely untested can be questioned. A program that is
formally verified may be trusted too quickly, even when the formal target omitted the requirement that mattered.

check passes if the original reconstructed target verifies the bad candidate with zero errors, and the repaired target fails verification
on the same bad candidate because the repaired constraint is not satisfied. These are local mechanism checks, not complete
repaired benchmark specifications.
3.3 Controlled benchmark and baseline mitigation
The controlled benchmark contains 12 executable tasks: 8 development tasks and 4 heldout tasks. Each task contains a public spec,
a separate policy pack, deterministic candidate implementations, and a hidden executable oracle representing intended behavior.
Each task is evaluated under three spec modes: naive incomplete specs, checklist-critic specs with common omissions addressed,
and oracle/full specs containing the intended requirements. Candidate selection is deterministic: the harness runs public-spec tests
against all candidates, keeps candidates that pass, and selects the first passing candidate in a fixed task order. The hidden oracle
runs only after selection. Because deterministic ordering could otherwise explain the results, we also analyze the full
public-spec-passing candidate set.
The Policy Audit Gate is a deliberately simple pre-selection baseline. It compares a public spec against a separate policy-card
inventory and returns ALLOW, REVIEW, or BLOCK. Both REVIEW and BLOCK stop automatic implementation selection. We use
the gate only as a simple known-policy baseline. It is not the main proposed solution and does not discover unknown requirements.
The Policy Audit Gate is a deterministic pre-selection checker that audits public spec text against task-linked policy cards from
configured policy packs. For each policy card, it assigns covered, unclear, or missing using explicit keyword/term matching, then
applies fixed decision rules: missing critical or load-bearing requirements trigger BLOCK, unclear high/critical requirements or low
high-severity coverage trigger REVIEW, otherwise ALLOW. In controlled calibration, hidden-oracle outcomes are used only as
external labels for metrics; hidden-oracle signals are not used to compute pre-selection decisions.
4. Results
 Main result. We find verified-but-wrong target-validity failures in public benchmark artifacts and reproduce the mechanism in a controlled benchmark.
In the external audit, 11 demonstrations were validated, including 3 direct-Dafny cases where bad candidates verify with zero errors. In the controlled
benchmark, naive specs produced 12/12 verified-but-wrong selections, while oracle/full specs produced 0/12.

5. Discussion and Limitations
Why this is not just "weak specs are weak"
The claim is not that incomplete specifications exist. The claim is that vericoding pipelines can turn incomplete specifications into
trusted selection targets.
A weak informal requirement is visibly weak. A weak formal target can look strong because it is associated with formal verification.
This creates a specific evaluation risk: a pipeline may report that an implementation verifies, while the more important fact is that the
target did not encode the intended behavior.
The missing question is therefore not only whether the implementation satisfies the spec. It is also whether the spec preserves the
intent it is supposed to formalize.
What the results do and do not show
The results show that verified-but-wrong failures can be realized in public benchmark artifacts and that the mechanism can be
isolated in a controlled benchmark. The external replication suite reduces cherry-picking risk by adjudicating all high-confidence
scanner candidates under a frozen labeling protocol.
The results do not estimate prevalence. The external replication suite is scanner-ranked and enriched for likely gaps. It is not a
random sample of all benchmark tasks. Only DA0003, DA0208, and DA0293 are direct-Dafny demonstrations against reconstructed
original benchmark targets. These cases cover simple underconstraint classes, so broader omission patterns remain supported
primarily by Tier 2 adapted demonstrations and the controlled benchmark.
The repaired-target checks are local mechanism checks. They show that adding the omitted target constraint blocks the same bad
candidate in the three Tier 1 cases. They are not full repaired benchmark specifications and do not imply that all external tasks have
easy repairs.
The controlled benchmark is author-constructed. It isolates the mechanism and mitigation behavior under controlled conditions, but it
is not an external prevalence estimate. The Policy Audit Gate is also not a complete solution. It depends on a maintained policy
inventory, can over-block when wording is outdated, and does not discover unknown requirements.
Why this is not oracle leakage or only candidate ordering
The hidden oracle is used only after candidate selection to evaluate intended behavior. The pre-selection audit sees the public spec
and policy inventory, but not the hidden oracle and not the selected candidate.
The failure is also not merely caused by selecting the first passing candidate. Under naive specs, 34 of 46 public-spec-passing
candidates failed hidden intended behavior. This shows that the public target underconstrained the candidate pool, not just the first
selected candidate.
Practical recommendation and dual-use considerations
Vericoding pipelines should add a target-validity check before implementation selection: start with natural-language or policy intent,
translate it into a formal/public spec, audit whether the spec preserves intent-critical requirements, repair missing or unclear
requirements, then generate and select candidate implementations.
The target-validity check should not be treated as a fully autonomous rejection mechanism. A safer deployment posture is
human-in-the-loop review: ALLOW specs proceed, REVIEW specs are repaired by a human, and BLOCK specs require explicit
policy-owner approval before candidate selection.
A tool that identifies missing specification constraints could be misused to craft under-specified tasks that evade weak selection
pipelines. The defensive use is to audit specs before implementation selection, surface missing requirements, and route risky specs
to review. If future audits identify live production issues, those issues should be disclosed privately to maintainers before publication.
6. Conclusion
Vericoding can verify that code satisfies a supplied specification. It cannot, by itself, guarantee that the supplied specification was the
right target.
We introduced verified-but-wrong as a target-validity failure mode: a selected implementation passes the public formal target but
violates intended behavior. Implementation validity asks whether the code satisfies the spec. Target validity asks whether the spec

preserves the intent.
In an external Dafny vericoding benchmark audit, we scanned 1,448 useful-description tasks and identified 128 candidate
target-validity gaps. We then adjudicated all 41 high-confidence candidates under a scanner-ranked external replication protocol.
This yielded 11 externally sourced demonstrations: 3 Tier 1 direct-Dafny cases and 8 Tier 2 adapted demonstrations. In the Tier 1
cases DA0003, DA0208, and DA0293, trivially wrong implementations verify against reconstructed original benchmark targets while
failing intended-behavior examples. Repaired-target checks block the same bad candidates in all three cases.
In a controlled 12-task benchmark, naive specs produced verified-but-wrong selections in 12/12 tasks, critic specs in 5/12, and
oracle/full specs in 0/12. Candidate-set analysis showed that the issue is not merely fixed ordering: under naive specs, 34/46
public-spec-passing candidates failed hidden intended behavior. A deterministic target-audit baseline caught 17/17 dangerous specs
with 0 dangerous allows and a 78.95% safe allow rate.
Before using a formal spec as a vericoding selection target, we should audit whether the spec is the right target.
If vericoding pipelines inherit the blind spots of their specifications, then target-validity auditing should happen before
implementation selection.
