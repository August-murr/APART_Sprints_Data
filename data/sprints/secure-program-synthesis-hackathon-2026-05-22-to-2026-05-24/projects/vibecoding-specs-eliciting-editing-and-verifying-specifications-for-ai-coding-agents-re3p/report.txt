Abstract
Specifications for real systems do not exist as one-shot artifacts: the user’s intent
emerges as they discover edge cases, rewrite drafts, and react to failing tests. We
present aniterative pipelinethat takes this seriously — every spec artifact (the
Lean predicate, the Python reference oracle, the generated code, the LLM-emitted
concrete test cases) is independently editable and individually re-verifiable. Each
round of the brief regenerates only the artifacts the reviewer asks for; the rest
are preserved. This operationalises Dodds’ position that “specifications don’t
exist” in the complete-and-coherent form formal-verification tools expect [1] —
the right tooling shape is iterate-and-export, not generate-and-ship. Concrete con-
tributions: (i) the iterative pipeline itself — editable Lean, code, oracle, and test
cases; (ii) LLM-emitted concrete test cases derived from the spec, run row-by-
row against the agent’s implementation; (iii) a behavioral + structuralinvariant
DSL; (iv) mutation testing for specifications; (v) Lean 4 generation of a struc-
tural Diff→Prop block and an algorithmic predicate over the function’s ar-
guments (e.g. def isNotPrime (n : Nat) : Prop := n < 2∨ ∃k, 2
≤k∧k < n∧n % k = 0 ), both type-checked by lake build ; (vi) Hypoth-
esis property-based testing of the agent’s code against the (editable) reference
oracle. On the 60-pair evaluation derived from prior work, our structured validator
reaches98.3% accuracy, 2.2% false-accept rate, and Cohen’s κ= 0.957 while
matching the strongest LLM judge at ∼300× lower wall-clock cost. The mutation
harness finds39.7% of perturbations load-bearingwith zero brittle mutations.
Cross-dataset experiments on five Python benchmarks spanning 2021–2025 (MBPP,
HumanEval, BigCodeBench, HumanEval Pro, LiveCodeBench) show 100% Lean
type-check across 25 problems, and a codegen-validation rate that improves from
40% to 92% after three targeted fixes. We trace the iterative pipeline end-to-end on
a deliberately under-specified word-wrap brief whose intent stabilised only after
four rounds of refinement, and use the simpler is_not_prime task to show the
same pipeline handling a clean one-shot intent. All code, the Lean prelude, the
evaluation harness, and a browser demo are released.

socket while editing a math utility), andscope creep(the code does what was asked and a lot of

A separate uncomfortable fact: even when an engineerhasthe intent in their head, they rarely have

every downstream artifact (Lean, code, oracle, tests) to a single elicitation pass also does not. The
realistic shape is one in which the reviewer can edit any one artifact and re-verify just that artifact —
the rest stays put.
This paper takes the position thatpartial, low-cost, machine-checkable, iteratively-authoredspecifi-
cations are achievable for the coding-agent setting even when complete specifications are not. We
contribute:
1. Aniterative pipeline(Section 3.2) where each spec artifact — Lean predicate, Python
implementation, Python reference oracle, LLM-emitted concrete test cases — sits behind
its own editor and its own re-verify button. The whole session exports as a single JSON
spec bundlewith every artifact in its current state. No prior coding-agent spec tool exposes
per-artifact iteration in this shape.
2. LLM-emitted concrete test cases derived from the spec without seeing the code
(Section 3.6). The same elicitation that produces the Lean predicate emits ∼8(input,
expected, rationale) triples; a subprocess runner executes them against the agent’s
implementation row-by-row. This is separate from PBT-vs-oracle: concrete cases are
reviewable by the human author and survive even when the oracle is absent or wrong.
3. Astructural invariant DSLof 6 invariant types (Section 3.1), authored as Python data-
classes with a median cost of 9 LOC and 120 seconds per task. Behavioral coverage (positive
tests) is bundled with structural coverage (diff-scoped invariants).
4. Abatch four-step pipeline(Section 3.3): ambiguous input → Lean 4 source → code
generation → structural validator + PBT round-trip. Shares all infrastructure with the
iterative pipeline and is the variant used for the cross-benchmark experiments in Section 4.
5. ALean 4 emitter and self-contained prelude(Section 3.4) that turns any task spec into
real .lean source type-checkable in ∼0.2s with lake build . Closes the call’s literal
“translate informal requirements into formal representations (e.g., Lean)”rather than waving
it away with “or similar.”
6. Amutation-testing harness for specifications(Section 3.7) that perturbs each invariant five
different ways and classifies the result as load-bearing, brittle, or invisible — the spec-side
analogue of code mutation testing.
7. Across-model and cross-source contradiction surfacer(Section 3.8) that re-drafts the
spec with a second LLM and flags every field where the two models disagree, plus a
per-source warnings panel.
8. A25-problem evaluation across 5 external benchmarks(Section 4.1) spanning 2021–
2025, with documented before/after numbers on a targeted LiveCodeBench improvement
that moves codegen-validation from 0/5 to 5/5.
How this differs from prior work.The individual pieces have been tried before, but never together
and never in an iterative shape: TiCoder [7] elicits a spec from NL as a single discriminating test;
nl2postcond [8] elicits Java postconditions; Kiro [4] adopts a three-artifact spec-driven model but
does not formalise and treats the artifacts as one-shot outputs; Lean Atlas [3] visualises a Lean
project for human semantic review but does not elicit; PRDJudge [9] scores agent outputs against a
PRD rubric but does not produce a checkable spec; SPEEDY [5] infers loop invariants from code
but starts from neither NL nor the agent setting. To the best of our knowledgeno prior system
supports per-artifact iteration(edit just the oracle, re-verify just the oracle)nor runs the full
elicit → formalise → validate → round-trip chainthe call’s requirements jointly demand. The
novel ingredients are: (a) the iterative pipeline shape itself with editable artifacts, per-button re-
verification, and JSON spec-bundle export; (b) LLM-emitted concrete test cases derived from the

2 Related work
Specifications don’t exist.Mike Dodds’ 2025 essay [1] argues that outside a few naturally-
formalisable domains (compilers, kernels, cryptographic libraries), formal specifications for real
systems do not exist andcannotexist in the complete-and-coherent form formal-verification tools
require. The PDF format is his recurring case study: every reader interprets ambiguous documents
slightly differently. Galois’ DaeDaLus / FAW [2] is the practical companion. Our work takes Dodds’
position as a design constraint: partial, machine-checkable specs are the realistic target.
Specification IDEs and elicitation pipelines. Lean Atlas[3] is a recently-announced human-
in-the-loop Lean 4 IDE that visualises the dependency graph of a Lean project and flags nodes
needing humansemanticreview — the type-checker only verifieslogicalcorrectness. We borrow
that distinction directly: our pipeline shows ✓ on lake build but emits provenance chips (explicit
/ inferred / default) on every drafted invariant.Kiro IDE[4] adopts a three-artifact spec model
(requirements.md in EARS notation, design.md, tasks.md); we mirror the artifact-as-file shape
with a spec.lean / requirements.ears toggle.SPEEDY[5] andTrustworthy Formal NL
Specifications[6] both pioneer per-clause traceability between English source and formal output;
our split-pane source↔spec linked view follows their pattern.
Spec-elicitation baselines. TiCoder[7] elicits a spec as one or more discriminating tests the
user approves.nl2postcond[8] uses LLMs to generate Java postcondition assertions on Defects4J
methods.PRDBench / PRDJudge[9] uses structured PRDs with per-criterion LLM rubrics; we
implement PRDJudge as our prd_style_judge baseline.FeatureBench[10] benchmarks feature-
level coding tasks but its corpus is gated. Our DSL differs from all of these by combiningbehavioral
coverage(positive tests, as in TiCoder) withstructural coverage(diff-scoped invariants, novel here).
Code-generation benchmarks.We adapt samples from five Python benchmarks:MBPP[11],
HumanEval[12],BigCodeBench[13],HumanEval Pro[14] (self-invoking variants), andLive-
CodeBench[15] (contamination-free contest problems).

3 Method
3.1 The structural invariant DSL
A TaskSpec is a frozen Python dataclass with four fields: a one-sentence description, a
starting_repo mapping path to source, a tuple of positive_tests (pytest-shaped), and a tuple
ofnegative_invariants. The library exposes six invariant types (Table 2).
Table 2: The six structural invariants and what each catches.
Invariant Catches
OnlyFilesModified(paths)Edits outside the named scope
FilesUnchanged(paths)Edits to files that must stay frozen
NoNewImports(forbidden)New imports ofos,subprocess, network libs
NoSecretsInDiff()AWS / Anthropic / GitHub keys, private-key blocks, passwords
DiffSmallerThan(n)Sprawling rewrites of small tasks
PositiveTestPasses(test)Behavioral oracle
Authoring cost on our hand-authored 15-task corpus ismedian 9 LOC, median 120s per spec.
The invariants are deliberatelystructuralrather than behavioral: the user reasons about which files
the change is allowed to touch and which imports it may not introduce, not about what the code
semantically does. This is what makes the partial-spec approach achievable at low cost.
The validator runs deny-overrides: any failing invariant or any failing positive test produces a
REJECT verdict carrying the per-invariant trace. To honour Dodds’ “potato of doom” zone we added
anABSTAINverdict for cases where the spec itself could not be evaluated (a test crashes on import,
an invariant check raises). The validator is deterministic, network-free, has no per-call cost, and runs
the 60-pair corpus in∼1.6s on a stock laptop.
3.2 The iterative pipeline
The iterative pipeline is the primary contribution of this paper. Its shape is dictated by the observation
in the introduction: the user’s intent is not complete on the first try, and the right tooling lets the
reviewer edit any one artifact and re-verify just that artifact without redoing the rest. The browser
demo’sIterative pipelinetab presents five collapsible sections, each backed by an editor and a
re-verify button:
1. Input.A free-text English brief (or a picked benchmark fixture), an editable starting repo
(main.py is the seed when nothing is loaded), and two optional reference fields — ground-
truth spec and ground-truth code — that the pipeline passes through to the export bundle but
does not use for validation. “Elicit spec” calls the same drafter as the batch pipeline.
2. Lean spec.The elicited .lean source — carrying both the structural Diff→Prop
block and the algorithmic predicate (Section 3.4) — appears in a textarea. “Syntax check
(lake build) ” runs Lean on the current buffer; on failure, the compiler trace is shown
verbatim. The reviewer can tighten the predicate (add a clause, weaken a bound) and
re-check without re-eliciting.
3. Python code.“ Generate code ” calls a lightweight codegen endpoint that emits Python
without immediately running the structural validator or PBT. The files are editable per-

tab; “Syntax check (ast.parse) ” is a cheap per-file SyntaxError report — enough
to catch the agent’s hallucinated indentation before any subprocess is launched.
4. Concrete test cases.“ Generate cases ” calls a separate elicitation that — given the
description and behavioral predicate butnotthe agent’s code — returns ∼8(input,
expected, rationale) triples. The reviewer can edit any cell or click “ + add empty
row” to inject a regression. “Run against current code ” materialises the edited code,
materialises the cases, and runs them in a subprocess; each row shows input | expected
| got |✓/×(Section 3.6).
5. Property-based testing.The Python reference oracle is itself a textarea, pre-filled from
the elicitation but immediately editable. A bright warning notes that the oracle was LLM-
synthesised and should be reviewed before trusting any PBT verdict; a “ Clear oracle
(skip PBT) ” button disables this section entirely when no oracle is appropriate. “Run PBT
vs oracle ” fuzzes the agent’s current code against the current oracle on 200 Hypothesis-
drawn inputs (Section 3.5). On falsification, the shrunken counterexample is shown inline.
A single “Export bundle ” button serialises the entire session — input, drafted invariants, Lean
source and verify result, code and syntax-check result, test cases and run results, oracle and PBT
verdict — into one JSON file. The bundle is the spec artifact: future runs, audits, or downstream
tooling all start from the same JSON.
Two design choices are worth flagging. First,no automatic chaining: editing the Lean does not re-run
the codegen; editing the code does not re-run the cases. Every verification is reviewer-triggered. This
keeps the cost of iteration linear in the artifacts the reviewer actually changed. Second,the oracle is
treated as part of the spec, not part of the verifier: a falsified PBT run with an LLM-emitted oracle is
a claim about the agent’s coderelative to a comparator the user is supposed to have read. Surfacing
the oracle as an editable textarea makes that responsibility explicit.
3.3 The batch four-step pipeline
For benchmarking we use a linear sibling pipeline that sequences elicit → Lean → code → val-
idate end-to-end with no human in the loop. The browser demo’s4-step pipelinetab and the
dataset-run CLI both call this variant. Each step uses the same modules as the iterative pipeline
(elicitation.py, lean_emitter.py, codegen.py, validator.py, verify_pbt.py); the only
difference is that the batch variant runs them in fixed order and emits a single ACCEPT/REJECT
verdict per task instead of asking the reviewer to inspect each artifact. All the cross-benchmark
numbers in Section 4 come from this batch variant; they are equally claims about the elicitation/Lean/-
codegen/PBT infrastructure that powers the iterative pipeline.
3.4 Lean 4 emission and verification
Each emitted.leanmodule carriestwoblocks:
Structural block.The bundled prelude ( safe_scaffold/lean_prelude/SafeScaffold/Basic.lean)
mirrors each structural invariant as a Diff→Prop predicate. The Diff structure has four fields
the predicates inspect: changedPaths, newImports, totalLines, addedStrings. The structural
block is the conjunction of the chosen Diff predicates:
def spec (d : Diff) : Prop :=
OnlyFilesModified d [...] /\
NoNewImports d [...] /\
DiffSmallerThan d N /\
NoSecretsInDiff d
Behavioral block.The elicitation pipeline additionally requires a behavioral_spec entry on
every drafted spec — a Lean predicate capturing the algorithmic content of the intent. For the brief
“Write a python function to identify non-prime numbers”, the LLM emits:
def isNotPrime (n : Nat) : Prop :=
n < 2 \/ exists k, 2 <= k /\ k < n /\ n % k = 0

described in Section 3.5, which fuzzes the agent’s code against a Python reference function the
elicitation emits alongside the Lean predicate.
3.5 Property-based verification against an LLM-emitted reference oracle
Once the algorithmic spec is fixed (Section 3.4), the question is whether the agent’s optimised Python
implementation realises it. For arbitrary Python this question is undecidable; in practice three tools
approximate it: CrossHair-style SMT, bounded-exhaustive testing, and property-based testing (PBT).
We ship PBT-against-oracle as the v1 because (a) Hypothesis is the de-facto standard for Python
property checks; (b) the comparator is itself elicited from the same intent so it is not a tautology; (c)
Hypothesis returnsshrunken counterexamplesso a reviewer can act on failures immediately.
Mechanism.Each behavioral_spec block carries three executable artifacts in addition to the
Lean predicate:
•function_nameandsignature— the Python contract the agent must export;
•python_oracle — a slow but obviously-correct Python reference implementation of the
same predicate, restricted to stdlib;
•input_strategy — a Hypothesis strategy expression (e.g. integers(min_value=0,
max_value=200)) drawing inputs.
The PBT runner ( safe_scaffold/task_spec/verify_pbt.py) materialises the agent’s code
and the oracle into a temp directory under separate module names, generates a self-contained
pytest+Hypothesis driver that imports both, and runs the driver in a subprocess for 200 examples.
Outcomes are verified (no counterexample), falsified (Hypothesis returned a shrunken CE),
or error (oracle threw / toolchain missing). The result is surfaced as a sixth “invariant” line in the
codegen verdict trace, sitting alongsideOnlyFilesModified,NoNewImports, etc.
Honest framing.A verified verdict means“200 random examples drawn from the input strategy
produced no counterexample”— strong evidence, not a formal proof. The safeguards against the LLM
emitting a wrong oracle are (i) the same elicitation also emits the Lean predicate, which a reviewer
can read independently; (ii) the cross-model spec comparison (Section 3.8) flags disagreements
between models, which catches oracle bugs that survive into multiple drafts. Compile-checking
the behavioral Lean is a separate guarantee from the PBT result — the former proves the spec is
well-typed, the latter that the implementationagrees with the oracle on tested inputs.
3.6 Concrete test cases elicited from the spec without seeing the code
Property-based testing requires an oracle and reports one shrunken counterexample on failure. A
complementary kind of evidence is a small set ofnamedtest cases that a human can read, edit, and
version — the kind of artifact that historically lives at the bottom of a JIRA ticket. Such cases are also
the right output when the brief evolves: a new clause typically translates into one or two new rows.
We synthesise these from the spec text. The elicitation call
(safe_scaffold/task_spec/test_case_gen.py) receives the description, the Lean pred-
icate, the function signature, and the Hypothesis input strategy; it doesnotreceive the agent’s
implementation. It returns a JSON array of ∼8 {input, expected, rationale} triples, where
each field is a Python literal expression validated by ast.literal_eval. The runner materialises

The cases are editable before they are run: a reviewer who finds the LLM’s expected values dubious

In our word-wrap walkthrough (Section 3.9.1) the LLM-generated cases catch all four kinds of
edge condition the brief evolved to express — single-line, multi-line-merged, multi-paragraph,
indent-preserving — before the PBT run is even attempted.
3.7 Mutation testing for specifications
We perturb each invariant in five ways: drop_invariant, weaken_bound (numeric), shrink_set
(set parameter), widen_scope, and drop_test. Each mutation re-runs the corpus candidates against
the perturbed spec and classifies the outcome as:
• load_bearing— at least one should-reject candidate is newly admitted. Direct evidence the
original invariant was earning its place.
• brittle— at least one should-accept candidate is newly rejected. The original spec was
barely tolerating CORRECT.
•invisible— verdicts unchanged.
This is the spec-side analogue of mutation testing for code: instead of perturbing the implementation
and asking “did tests catch it?” we perturb the spec and ask “did the candidate corpus catch the
weakening?” Per-speccoverage scoreis the fraction of mutation kinds with at least one load-bearing
case — a Dodds-aligned honesty metric.
3.8 Cross-source contradiction surfacer
When the elicitation receives multiple sources (intent + prose doc + existing tests + slide deck), the
LLM is required to additionally emit a contradictions array — entries of the form {sources,
summary, resolution} . In our hand-crafted Brief B (a PRD that requires bcrypt-hashed passwords
and“store exactly as provided so support can read them back”and“no new dependencies”and
“use bcrypt”) the LLM consistently identifies both internal contradictions and emits a deliberate
side-taking resolution. The contradictions panel is rendered yellow before the drafted invariants so
reviewers see the muddiness before they see the proposed spec.
Example.For Brief B (intent “Add password hashing to the user signup flow” plus a deliberately
self-contradictory PRD), the elicitation API returns the following contradictions array:
[
{
"sources": ["intent", "prose_doc"],

3.9 Worked examples
We trace two complete iterative sessions end-to-end against the released code. Example 1 (§3.9.1) is

3.9.1 Example 1: iteratively specifying word wrap
The brief evolves.The intent started as a one-line English sentence and grew clause by clause across

def word_wrap(text: str, width: int) -> str:
paragraphs = text.split(’\n\n’)
result_paras = []
for para in paragraphs:
lines = para.split(’\n’)
first_line = lines[0] if lines else ’’
indent = ’’
for char in first_line:
if char == ’␣’: indent += char
else: break
words = []
for line in lines:
words.extend(line.strip().split())
if not words:
result_paras.append(’’); continue
wrapped_lines = []
current_line = indent + words[0]
for word in words[1:]:
if len(current_line) + 1 + len(word) <= width:
current_line += ’␣’ + word
else:
wrapped_lines.append(current_line); current_line = word
wrapped_lines.append(current_line)
result_paras.append(’\n’.join(wrapped_lines))
return ’\n\n’.join(result_paras)

4.6 The LiveCodeBench fix
The initial 40% pass rate (LCB at 0%) revealed three avoidable failure modes that the pipeline’s
per-invariant trace made precisely diagnosable:
1. The LLM-invented positive test did not match the benchmark’s canonical I/O contract. On
LCB this was catastrophic — contests are stdin/stdout-shaped and the LLM’s invented
assertions used different I/O conventions.
2. The function stub did not communicate the I/O contract. “Implement solve” was ambigu-
ous; some models wrote functions that took a list of strings, others calledinput()/print()
directly.
3. The codegen response parser was too strict to handle <answer>-tag-wrapped JSON output
— several models prefaced the JSON with reasoning text.

Three targeted fixes brought the combined score to92%, with LCB at100%:
1. Pre-author the positive test from each benchmark’s canonical tests.LCB ships
public_test_cases with the exact contest I/O; we parse it into a real pytest and pass it as
a new override_positive_test= parameter to draft_spec. The LLM still drafts the

2. Explicit contract in the stub.The LCB stub now says verbatim: “Convention: read

3. Lenient JSON extractor + stricter prompt.A new _extract_json_object tries the

5 Discussion
Iteration is the missing affordance, not just polish.Watching reviewers use the iterative tab
makes one observation routine: the brief they start with is never the brief they end with. The word-
wrap example evolved across four rounds; even the simpler is_not_prime example benefits from the
editable oracle (a reviewer who is suspicious of the LLM’s choice ofany(n % k == 0 for k in
range(2, n)) can rewrite it to any(n % k == 0 for k in range(2, int(n**0.5)+1)) and
re-run PBT in seconds). Locking these artifacts behind a one-shot generate-and-ship interface — as
Kiro, TiCoder, and the batch four-step pipeline do — is what makes spec authoring feel like fighting
the tooling.
Lean emission is 100% reliable; codegen is not.Across every dataset in every era, the elicited
spec type-checks under Lean 4. This is exactly the Lean Atlas blind spot [3] — structural well-
formedness does not catch semantic under-specification. The codegen round-trip is what surfaces
semantic gaps: when the LLM-generated implementation fails the spec’s own positive test (or its
concrete cases, or its PBT-against-oracle), the per-invariant trace tells the reviewerwhichlayer was
inadequate and how.
The improvement strategy generalises.The override_positive_test hook is dataset-
agnostic. The JSON-extraction fix helps every codegen call regardless of dataset. The lesson
—do not delegate the oracle to the model; pre-author it when the dataset provides one— is general.

Provenance chips are the missing review interface.Of our 25 cross-dataset runs, every drafted
spec contains at least one default-grounded invariant the LLM filled in without evidence. Surfacing

6 Limitations
• The mutation harness’s widen_scope uses candidate-derived paths to remain informative;
a blind variant would need curated scope-creep-shaped filename pools per category.
• All mutations are structural; semantic perturbation (e.g. inverting an assertion) is unimple-
mented.
• The complex hand-authored corpus is 3 multi-file tasks (12 pairs) — small relative to
FeatureBench’s 200 tasks.
•lake build verifies logical, not semantic, correctness of emitted Lean.looksLikeSecret
isopaquebecause regex matching onStringis heavy to model.
• External-dataset adapters are shallow for benchmarks without canonical tests. Only Live-

manEval ship test cases we use asexisting_testssources but not as the oracle.
• Sample size on the 5-dataset run is 5 problems each (25 total). Headline numbers are best
read as proof-of-concept, not a benchmark result.
7 Conclusion
Specifications for real systems emerge through iteration, not as one-shot artifacts. The right tooling
shape for AI coding agents is therefore one in which the reviewer can edit any one artifact —
Lean predicate, generated code, reference oracle, concrete test cases — and re-verify just that
artifact without redoing the rest, then export the whole session as a single JSON spec bundle. We
present an iterative pipeline of this shape, alongside a batch four-step sibling that uses the same
modules for benchmarking. On a 25-problem cross-dataset sample spanning 2021→2025 the batch
pipeline reaches 100% Lean type-check and 92% codegen-validation after a small number of targeted,
auditable fixes; the iterative pipeline absorbs four-round brief refinement on a word-wrap task we trace
end-to-end. A deliberately partial structural-invariant DSL underlies both, drafted from ambiguous
English in seconds, emitted as real Lean 4 type-checkable in 0.2 s, mutation-tested to surface which
invariants are doing real work, and cross-validated against a second LLM to flag under-specified
fields.
Future work: (i) a Dafny / F* back-end alongside Lean to compare formal-target ergonomics; (ii) a
larger-scale FeatureBench / PRDBench run once access becomes available; (iii) semantic mutation
operators (assertion inversion, parameter swap) to complement the current structural mutation harness;
(iv) integration with a real PR-review surface (GitHub Checks) so the per-invariant trace lands in the
agent’s actual workflow.
