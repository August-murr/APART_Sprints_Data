SpecCheck: When LLMs Formalize, Who Checks the Spec?1
Bhagyesh Kumar
MIT Manipal
With
Apart Research
Abstract
Proof checkers guarantee that code satisfies a specification, but not that the
specification captures what the user intended. When large language models
formalize natural language requirements, they can silently weaken postcon-
ditions, drop edge cases, or resolve ambiguous terms in ways the user did
not expect: a failure mode we callintent drift. We present SpecCheck, a
pipeline that detects intent drift through two complementary techniques:am-
biguity elicitation, which surfaces implicit assumptions before formalization,
andround-robin cross-validation, where two independent models each formal-
ize the same requirement and informalize the other’s output. Across Lean 4
theorems (VERINA) and Python Hypothesis property suites, we find that the
value of cross-model validation is formalism-dependent: on Lean 4, it exposes
under-formalization that single-model assessment systematically misses (20-
percentage-point gap), while on property-based tests, single-model assessment
is already well-calibrated. The full pipeline achieves a 97% confirmation rate
on correct specifications and 100% detection on deliberately weakened ones.
Ambiguity count at elicitation time predicts which requirements will cause
trouble downstream, flagging difficult requirements before formalization.
1 Introduction
A proof checker can guarantee that code satisfies a specification. It cannot guarantee that the specification
captures what the user intended. This distinction has always mattered, but it becomes acute when large
language models (LLMs) are used to translate natural language (NL) requirements into formal specifi-
cations: property-based tests, Lean 4 theorems, or Dafny pre- and postconditions. LLMs can produce
plausible formalizations in seconds, but their output requires human judgment to verify faithfulness.
Manual validation does not scale.
The failure mode is intent drift: a generated specification can be formally valid, provably satisfiable,
logically consistent and yet miss edge cases the user considered obvious, permit behaviors the user
intended to forbid, or resolve ambiguous terms in ways the user did not expect. Proof checkers cannot
detect these gaps. The proof is correct relative to the specification, but the specification may fail to capture
the intended semantics.
Graciolli and Amin [3] introduced claimcheck, a round-trip detection approach: a model informalizes a

formal specification back to natural language, and a judge compares the result to the original requirement.
This detects many forms of drift. But single-model round-tripping has a structural blind spot. If a model
assumes that “sorted” means non-decreasing and carries that assumption through both formalization and
informalization, the round-trip appears clean. The specification is wrong, but no signal surfaces.
SpecCheck addresses this through two complementary mechanisms. First, ambiguity elicitation enumer-
ates implicit assumptions and underspecified terms before any formalization occurs. A requirement like
“merge two sorted arrays” leaves unspecified whether the output must itself be sorted, or merely contain
all elements. By surfacing this ambiguity upstream, the user can clarify intent before it is silently resolved
incorrectly by a model. Second, round-robin cross-validation uses two independently operating models:
each formalizes the same NL requirement separately, then informalizes the other’s output. Disagreement
between informalizations provides a drift signal inaccessible to single-model pipelines. When one model
writes a postcondition checking only set membership and the other additionally requires sorted order,
the weaker specification is exposed not because it fails a proof, but because a second model reads it and
notices what is missing.
Our main contributions are:
1. Ambiguity elicitation as a pre-formalization stage: a structured pass that enumerates implicit
assumptions before formalization, surfacing drift that round-tripping misses when both models share
the same prior.
2. Round-robin cross-validation: two independent LLMs formalize the same requirement and each
informalizes the other’s output, providing a cross-model drift signal unavailable to single-model
pipelines.
3. Empirical evidence for formalism-aware validation: cross-model disagreement provides substantial
additional signal for Lean 4 specifications, where single-model assessment misses under-formalization;
for property-based tests, single-model assessment is already well-calibrated and cross-validation adds
no systematic benefit.
We describe the SpecCheck pipeline and experimental conditions (§3), present results across both domains
(§4), and discuss implications for formalism-aware validation together with limitations of the current
evaluation (§5).
2 Related Work
Claimcheck.Graciolli and Amin [ 3] introduced blind round-trip informalization for detecting intent
drift in Dafny formalization, and independently recovered corrections that later appeared in the FOLIO
benchmark’s second version. SpecCheck extends this to the generative setting: rather than validating
existing specifications, it validates the formalization process itself, adding cross-model disagreement as a
detection signal that single-model round-tripping structurally cannot provide.
NL-to-spec translation.Cosler et al. [ 1] show that structured ambiguity elicitation improves NL-to-
temporal-logic translation; Endres et al. [ 2] document systematic postcondition weakening by LLMs.
SpecCheck builds on both: it elicits ambiguities upstream and detects the weakened-postcondition
patterns Endres et al. describe.
Verifier-backed and closed-loop pipelines.Clover [6] treats specifications as trusted ground truth for
code generation; SpecGen [ 4] prunes candidate postconditions using verifier counterexamples. Both
operateafterformalization, checking provability or correctness against code. SpecCheck instead asks
whether the specification matches the NL requirement. Cross-model critique [5] provides the mechanism:
critique by a different model reduces self-confirmation bias inherent in single-model pipelines.

3 Methods
3.1 Pipeline Overview
SpecCheck processes each NL requirement through five sequential stages, using claude-haiku-4-5
as model A andclaude-sonnet-4-5as model B and judge. 2
Stage 0—Ambiguity Elicitation.Before any formalization, model A enumerates implicit assumptions
in the NL requirement: undefined or context-dependent terms, unstated boundary cases, type or range
assumptions, and ordering assumptions. The output is a structured list of 1–5 ambiguities. In interactive
use, these are presented to the user for clarification before proceeding; in our automated evaluation, they
are recorded but the original NL is left unchanged, allowing us to measure whether ambiguity count
predicts downstream disputes.
Stage 1—Independent Formalization.Models A and B each independently formalize the same NL
requirement without seeing each other’s output. For Domain 1 (VERINA), the target is a Lean 4
precondition–postcondition pair with a theorem statement. For Domain 2 (Hypothesis), the target is a
Python property-based test suite using@givendecorators with appropriate strategies.
Stage 2—Cross-Informalization.Model A informalizes B’s specification, and model B informalizes
A’s specification. Neither model sees the original NL requirement during this stage—only the formal
specification written by the other model. Each informalization must describe what the specification
literally states, note which edge cases are and are not covered, and rate the specification’s strength (trivial,
weak, moderate, or strong).
Stage 3—Round-Robin Judgment.The judge (model B) receives the original NL requirement alongside
both back-translations. It scores each on five dimensions: completeness, precision, scope, edge-case
coverage, and implicit-assumption handling, assigns a drift score in [0,1] , and labels any drift found
with a type from {tautology, weakened-postcondition, narrowed-scope, missing-case, wrong-property}.
These labels are enforced by the tool’s JSON schema: the judge selects from a fixed closed set and cannot
produce labels outside it, bounding free-form inconsistency. It also flags whether the two independently
generated specifications disagreed on what to formalize.
Stage 4—Aggregation.A requirement isconfirmedonly if both back-translations are judged to match
the original NL requirement; otherwise it isdisputed. The pipeline also records which signal contributed
to each dispute: round-robin disagreement, high ambiguity count ( ≥2 flagged assumptions), both, or
neither.
Because all benchmark specifications are human-verified, confirmation rate measures the pipeline’s
tendency to avoid falsely disputing correct specifications rather than specification correctness itself. We
evaluate four conditions that selectively enable these stages (§3.2), across two benchmarks (§3.3).

informalizer and judge roles here, which differs from claimcheck’s original setup where those roles are
separated; this conflation may inflate confirmation rates relative to a fully separated baseline.
• B2 (round-robin only):Dual formalization and cross-informalization active; no ambiguity elicitation.
• B3 (ambiguity only):Ambiguity elicitation active; model A formalizes; model B informalizes blind

3.3 Benchmarks
We evaluate on two domains that represent distinct points on the formalism spectrum: Lean 4, a
dependently-typed proof assistant where specifications must capture deep algorithmic structure, and
Python Hypothesis, a property-based testing framework where specifications are typically short, behav-
ioral, and grounded in concrete input–output checks.
Domain 1—VERINA (50 tasks).We sample 30 basic and 20 advanced tasks from VERINA [ 7] (seeds
42 and 43), covering array operations, string processing, mathematical predicates, sorting, search, and
algorithm problems. All tasks have human-verified correct specifications.
Domain 2—Hypothesis (50 tasks).We combine 21 tasks derived from Python standard library doc-
strings (sorted, str.split, set and dict operations, Counter, map, filter, enumerate, math
builtins) with 29 handcrafted specifications covering deduplication, binary search, flatten, running max-
imum, group-by, rotation, chunking, merge-sorted, sliding window, transpose, interleave, partition,
cumulative sum, palindrome check, and compact. Gold suites and injected bugs (three per task) are
included in the repository for future recall evaluation; this paper reports calibration only.3

is a false positive.Confirmation rate= 1 − false-positive dispute rate: higher is better on these
benchmarks. A pipeline that confirms everything scores 100% but has zero recall; a pipeline that disputes
everything scores 0% but has no precision. The sensitivity evaluation (§4.3) provides the recall estimate
on known-bad specs.

4.4 Sensitivity: Detection of Known-Bad Specifications
To assess whether the low false-positive rate comes at the cost of sensitivity, we constructed 10 manually
weakened Hypothesis specifications—each a variant of a gold spec with a single deliberate drift injected—
and ran SpecCheck (B4 configuration) on them. Drift types covered: weakened-postcondition (6),
missing-case (3), and tautology (1). SpecCheck disputed all 10 (100%), correctly identifying the drift
type in each case. Representative detections: the strict-inequality variant of sorted order (“<”
instead of “≤”) was flagged as wrong-property; the length-only variant of sorted permutation was
flagged as weakened-postcondition; the stability variant omitting relative-order checking was flagged as
missing-case. This confirms that the 97% confirmation rate on correct specifications is not an artifact
of over-permissiveness: the same pipeline that avoids false positives on correct specs reliably disputes
structurally weakened ones.
4.5 Cross-Provider Replication
To address the same-model-family concern, we reran B2 and B4 on VERINA replacing model B (sonnet)
with GPT-4o via OpenRouter, keeping model A (haiku) and the judge (sonnet) unchanged.

regardless of model diversity.
4.6 Qualitative Analysis
Case A—Round-robin detects what ambiguity elicitation alone misses (VERINA, merge-sorted-
arrays).Model A’s postcondition checks only set membership ( ∀x∈a, x∈result ), while model B
additionally requires sorted order and multiset equality. In cross-informalization, model B reading model
A’s specification reports that “ordering is not constrained.” Condition B2 correctly disputes this task.
Condition B3, in which model A self-informalizes, confirms it—demonstrating the self-confirmation
failure mode that cross-validation is designed to detect.
Case B—Ambiguity as a leading indicator (Hypothesis, str split whitespace).Stage 0 flags
three independent assumptions: which characters constitute whitespace, behavior on whitespace-only
strings, and what formally constitutes a “run” of whitespace. Both B2 and B3 dispute this task across
all runs. The high ambiguity count correctly predicted this as the hardest requirement in the benchmark
before any formalization was performed.

5 Discussion and Limitations
5.1 VERINA: Cross-Model Validation Provides Essential Signal
The 20-percentage-point gap between B1 (100%) and B2 (80%) on VERINA shows that cross-model
validation catches what single-model assessment misses. B1 confirms every task because the judge
accepts its own informalization as faithful, it sees what it produced, not the specification directly. B2
breaks this loop: model B reads model A’s specification and notices what is absent. Five advanced tasks
are disputed this way: LCS length, k-most-frequent elements, longest consecutive sequence, peak-valley
pattern, and merge-sorted-arrays, where model A writes property-only postconditions and model B
independently adds structural constraints like sortedness and multiset equality.
B3 and B4 both confirm 97.3% of tasks, recovering 17.3 points relative to B2. Without deliberately
weakened specifications, we cannot rule out that B3/B4 are under-disputing rather than B2 over-disputing.
But qualitative inspection supports the former: on the five disputed tasks, model A’s postconditions are
incomplete, and model B’s specifications independently capture what the requirements demand. B2
appears to provide a stricter, higher-recall signal; ambiguity elicitation in B3/B4 may soften the judge’s
threshold rather than resolve the underlying gap.
5.2 Hypothesis: Single-Model Assessment Is Already Well-Calibrated
On the Hypothesis benchmark, all four conditions fall within three percentage points of each other
(84.0–86.7%), with run-to-run variance exceeding condition-to-condition differences. Property-based
test suites are short, behaviorally grounded, and straightforward to informalize faithfully. When both
models produce specifications with equivalent property coverage, as they do for most stdlib-derived
tasks, cross-model disagreement adds no systematic detection benefit. The practical implication is
formalism-aware deployment: round-robin cross-validation is essential for proof-assistant specifications,
where models diverge on algorithmic structure, but appears unnecessary for simple property-based tests,
though larger studies with varied model pairs are needed to confirm this boundary.
5.3 Ambiguity Elicitation as a Leading Indicator
Across both domains, requirements flagged with two or more assumptions in Stage 0 disputed at
substantially higher rates than those with zero or one flagged assumptions (Table 3). The sole requirement
with three or more flagged assumptions—str split whitespace—was the only task disputed in
every condition across all three runs. This indicates that ambiguity count at elicitation time functions as a
practical upstream signal: before any formalization is attempted, users can identify which requirements
are likely to produce drift and invest additional clarification effort where it matters most. Critically, this
signal is available even in the single-model setting (B3), where cross-model disagreement is not.
5.4 Limitations
Sensitivity evaluated on hand-crafted drift.The 10 deliberately weakened specifications in §4.3 were
constructed by the authors, not independently generated by an LLM and verified to be wrong. A stronger
sensitivity evaluation would sample LLM-generated specs, have human annotators label them as drifted
or faithful, and measure recall on that set. The 100% detection rate on hand-crafted cases establishes that
the pipeline is not trivially permissive; it does not establish that all real-world drift patterns are equally
detectable.
Same model family and circularity risk.Haiku and sonnet share training data and methodology.
Additionally, the same model family both identifies ambiguities at Stage 0 and judges disputes at Stage 3,
creating a potential circularity: requirements flagged as ambiguous may be judged more harshly by
a model predisposed to find them problematic. A preliminary cross-provider replication (§4.4) with
GPT-4o as model B confirms that shared blind spots exist: B2 drops a further 12 points when using a

cross-provider pair, validating this concern. Stages 0 and 3 remain same-family in that run; breaking
those dependencies is a direction for future work.
Scale.Fifty tasks per domain with three runs is sufficient to observe the 20-point gap on VERINA, but
still modest for the Hypothesis equivalence claim. Ablation conditions (B1–B3) were run on the first 25
tasks only. Larger benchmarks are needed before concluding that cross-model validation adds no value
for property-based tests.
Tautology false positives.One B4 run on Hypothesis produced 7 tautology disputes; other B4 runs
averaged 0.5. The judge misclassified compact but correct properties—length preservation, element
existence—as tautologies when back-translations emphasized their trivial form. Targeted few-shot
calibration in the Stage 3 prompt is the direct fix.
5.5 Future Work
A natural next step is scaling the sensitivity evaluation: sampling LLM-generated specs, annotating them
for drift, and measuring recall on that set. Beyond this, several techniques from the original claimcheck
research agenda remain to be integrated. Formal equivalence checking between independently generated
specifications would provide a deterministic complement to LLM judgment; on failed checks, automated
counterexample generation could produce concrete inputs distinguishing the two specifications, giving
users interpretable evidence of divergence rather than a drift score. Mutation testing—deliberately
weakening implementations and checking whether disputed specifications catch the injected bugs—would
close the loop between spec quality and bug-finding ability. Longer-term: cross-provider model pairs to
amplify the round-robin signal, expansion to Dafny and Verus as target formalisms, and IDE integration
so that ambiguity elicitation and validation happen inline during specification authoring.
6 Conclusion
SpecCheck demonstrates that cross-model disagreement is a practical, verifier-free signal for catching
intent drift in LLM-generated specifications. The central finding is that this signal’s value depends on
the formalism: essential for Lean 4, where models silently diverge on semantic choices, but unnecessary
for property-based tests, where single-model assessment is already well-calibrated. This suggests that
validation pipelines should be formalism-aware rather than one-size-fits-all. Ambiguity elicitation
provides a complementary signal that works in both settings: requirements flagged with multiple implicit
assumptions are substantially more likely to produce drift, giving users an actionable warning before
any formalization is attempted. The current evaluation is limited in scale and uses same-family models
for most stages; larger benchmarks, cross-provider pipelines, and integration with formal equivalence
checking are natural next steps.
