Specs Are All Y ou Need: Leveraging LLMs, Lean,
and POSIX/W3C Specs to Find Bugs in Coreutils
and WebKit/Safari
Authors:Chad Brewbaker and Suhaas Teja VijjagiriAffiliation:The Secure
Program Synthesis Hackathon, May 2026
Abstract
We demonstrate that grounding LLMs with authoritative specification documents
and Lean 4 theorem proving produces meaningful software quality improvements
on long-standing, widely-deployed codebases. Using only POSIX SUSv4-2018,
RFC, WHATWG, and W3C specifications as our grounding material – plus Lean
4 source code for additional LLM grounding – we found 14 specification-level bugs
in WebKit/Safari parsers and 4 confirmed implementation bugs in MIT Rust
coreutils. Our three-layer methodology (source analysis, spec grounding, formal
verification) revealed systemic patterns: unchecked I/O return values across 205+
utilities, underspecified security defaults in RFC 8941 SameSite cookies, and
complete absence of parsing rules for FTP LIST output. Two independent wc
formalizations – our I/O-focused approach and the coauthor’s spec-to-theorem
empirical testing – converged on complementary bug categories, demonstrating
the robustness of the methodology. This work shows that technical specifications,
when formally interpreted through LLM-assisted theorem proving, serve as both
correctness oracles and specification improvement tools for codebases that have
never been formally verified.
1. Introduction
WebKit/Safari and POSIX core utilities are foundational infrastructure: one
serves billions of users through every modern browser, the other underpins every
Unix and Linux system. Both have been maintained for decades, both are widely
trusted, and neither has been formally verified.
We asked:Can LLMs, guided by authoritative specifications and Lean 4 theorem
proving, find real bugs in these mature codebases?Our answer is yes. Using
only publicly available RFCs, WHATWG/W3C specifications, and SUSv4-2018
as grounding material – we produced formal specifications that surfaced 14
specification ambiguities and 4 confirmed implementation bugs.
Our contributions:
1. 15 WebKit parser modules formalized in Lean 4 (5,441 lines, 207 theorems),
revealing 14 specification bugs including 2 CRITICAL security issues in
SameSite cookies and FTP LIST format.

2. Related Work
LLM-assisted formal verification.Prior work has explored LLMs for proof
generation (LeanDojo, ProofNet) and specification extraction from natural
language. Our work differs by using LLMs as aspecification-grounded bug-finding
toolrather than a proof automation engine – the LLM reads the RFC/POSIX
spec, writes the Lean formalization, and the process of formalization itself
surfaces bugs.
WebKit security analysis.Fuzzing (OSS-Fuzz) and symbolic execution
(KLEE) have found WebKit bugs, but these approaches test implementations
against expected behavior. Our approach is complementary: we formalize the
specification first, then check both spec and implementation. This reveals spec
bugs that no fuzzer would find.
POSIX compliance.Existing POSIX checkers verify API usage but do
not model I/O semantics. Our Lean specifications model return values, error
conditions, and buffering behavior – enabling proofs about program behavior
under failure.
What distinguishes our approach:We use LLMs to translate authoritative
specifications into executable Lean 4 theorems, then use the formalization process
itself to discover that the specifications are incomplete or contradictory. The
bugs we found exist in specs that have governed software for decades.
3. Methodology
Three-Layer Verification Framework
1. Source analysis: Read the implementation (WebKit C++, POSIX C,
Rust uutils) to understand actual parsing and I/O logic.
2. Specification grounding: Locate the governing standard (RFC,
WHATWG, W3C, SUSv4-2018) and extract ABNF grammars, algorithmic
descriptions, and normative requirements.
2

3. Formal specification: Write Lean 4 functions mirroring the implemen-
tation, grounded in the spec. Each ABNF rule maps to a Lean function;
each normative requirement maps to a theorem.
Two Independent wc Formalizations
Our project as a “toy problem”, formalized wc through anI/O semantics
approach(modeling BufRead, splice, fstat, exit codes – 889 lines across 8 files),
and aaspec-to-theorem approach: extract POSIX requirements, express as
Lean theorems, then empirically test against the uutils binary (4 modules, 21
tests).
These different approaches found different bugs – demonstrating that
specification-grounded formalization is robust to methodological choices.
What Didn’t Work According to Hermes Agent with Qwen3.6 27B
discribing difeculties it ran into
• Automated ABNF-to-Lean: ABNF repetition counts and grouping
don’t map cleanly to Lean functions.
• String-based parsing: Lean’s String is not a data type, preventing
structural induction. We switched to List Char operations. (Finding
found by Qwen3.6 27B attempting to explain it’s struggles with LEAN4
syntax)
• Naive decideproofs: Parser theorems require unfolding multiple function
layers. Customsimplemmas were needed.

Core Utilities: Systemic I/O Bug Pattern
515 utilities surveyed across 8 directories. 316 have critical I/O gaps – they use
I/O functions whose return values are not checked:

This is a decades-old pattern: when stdout encounters a write error, utilities
continue silently producing incomplete output. POSIX requires checking return
values, but 205+ utilities do not.
wc: Two Approaches, Four Confirmed Bugs
Our I/O-focused formalization(889 lines, src/uu/wc/formal/): - BUG-
1: splice() EINTR returns partial byte count (signal interrupts counting) -
BUG-3: 32-bit overflow on files > 4GB (usizewraps on 32-bit systems)
Coauthor’s spec-to-theorem approach(github.com/suhaasteja/wc-formal-
spec): - BUG-A: -c and -m accepted together despite POSIX mutual exclusion
(wc [-c|-m] ). uutils silently accepts both, produces ambiguous output, exits 0.
- BUG-B: On unicode input with-c -m , -c is silently dropped and a mysterious
count (matching neither bytes nor chars) appears in the second field.
The two approaches found different categories of bugs: ours found I/O path issues
(splice, overflow), the coauthor’s found spec compliance issues (flag handling,
counting logic). Together they provide more comprehensive coverage than either
alone.

5. Scaling and Conclusions
How This Scales
1. Template generation: ~40% of each Lean file is boilerplate (character
classes, string helpers). A library could help here. These are due to Hermes
Agent and Qwen3.6 writing boilerplate specs then refining them.
2. Modular theorem organization: HTTPRange (51 theorems) and wc
(30+ theorems across 4 modules) show large theorem sets are manageable
when split by category (character classes, parsing, edge cases, integration).

Thesis Restated
Grounding LLMs with authoritative technical specifications and Lean 4 theorem
proving produces meaningful software quality improvements on codebases that
have never been formally verified. The process of formalization itself is a
specification improvement tool: we found 14 bugs in specs that have governed
software for decades.
The convergence of two independent wc formalizations – using different method-
ologies but the same grounding principle (specs as ground truth) – demonstrates
that this approach is robust. Different methods find different bugs; together
they provide comprehensive coverage.
The formal specifications serve dual purposes: ascorrectness oracles(verify-
ing implementations match specs) and asspecification improvement tools
(identifying ambiguities in the governing standards). This dual role makes the
investment productive even before all theorems are proven.
