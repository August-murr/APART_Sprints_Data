Syscon: Kernel-Level Syscall Monitoring for
AI Agent Control in Sandboxed Environments ∗
Jade Sheffey1, Joyce Levine1, Willow Taylor1, and Joyce Werhane1
1University of Massachusetts Amherst
With Apart Research
Abstract
Many existing AI control protocols rely on atrusted monitorto evaluate an untrusted
agent’s actions, but these monitors generally access tool call invocations and context, not what
the agent actually does at the system level. We identify this as a fundamental information
gap in the control stack and present Syscon, the first system to close it. Syscon is a
supervisor-side auditor daemon that monitors agent activity at the Linux kernel syscall
boundary, leveragingseccomp-bpf audit logging fromoutsidethe agent’s container to observe
all process creation, network connections, and filesystem operations, all without running
any code inside the container and without the agent’s knowledge. The system produces
compressed, per-actionreceiptsdesigned for consumption by a trusted monitor LLM. We
evaluate Syscon on 234 attack trajectories across 9 attacker models in the LinuxArena control
evaluation framework. Our qualitative analysis confirms that receipts surface behavioral
signals (credential file reads, payload staging, reverse shell listeners, data exfiltration) that
are invisible in tool call text, covering multiple side task categories. However, a first-pass
integration with a Gemini 2.5 Flash monitor did not improve detection rates, establishing
thatobservability and detection are distinct research problems: Syscon receipts carry signal,
but monitors must be taught to use it.
1 Introduction
When an AI agent runs a shell command inside a container, the trusted monitor sees the
command text, and occasionally some context. The kernel sees hundreds of system calls (process
forks, network connections, file operations, IPC communication), any of which could be part of
an attack. This paper gives the monitor access to the kernel’s view without introducing undue
overhead to the evaluation environment.
AI companies are beginning to deploy autonomous agents to automate complex software
engineering and system administration tasks [9]. These agents operate by issuing shell commands
on target hosts, where they require broad permissions (root access, network connectivity, package
installation) to accomplish their work. As agent capabilities scale, so does the risk that a
scheming [3], backdoored [7], or otherwise misaligned model could abuse these privileges to cause
serious security failures.
AI control[5] techniques reduce the probability that such failures occur, even under the
worst-case assumption that the deployed model isactively attempting to subvert safety measures.
Rather than relying on alignment guarantees, control protocols treat the model as untrusted and
construct external safeguards such as monitoring, auditing, and resampling that make it harder
for a misaligned agent to succeed before being caught. Recent work has demonstrated this

agent’stool call text. As Kaufman et al. [9] observe, successful attacks work by “creating deep
and complex call stacks, so that the monitor cannot trace all of the data flows and no individual
data flows look locally very suspicious.” The monitor sees the commands the agentdeclares, but
not what those commands actuallydoat the system level (see fig. 1 for a concrete example).
1.1 Threat Model
We adopt the adversarial game formulation from prior control evaluations [5, 2, 9]. Ared team
constructs an attack policy that attempts to accomplishside tasks(security failures such as data
exfiltration, malware execution, or privilege escalation) while completing legitimatemain tasks.
Ablue teamconstructs control protocols that detect and prevent side task completion without
degrading the honest agent’s usefulness. Safety is measured as the probability that an attack is
detected before it succeeds [9].
The threat landscape for agents with shell access is broad and largely invisible to text-level
monitoring. We highlight five categories:
1. Data exfiltration:An agent may read credentials under the guise of legitimate operations
(e.g. a shell glob likecat /home/app/.* captures dotfiles without naming them), then
exfiltrate data via network channels (curl -X POST, DNS tunneling, or reverse shell
listeners likencat -l -p 4444) that produce no visible command output.
2. Supply chain exploitation:Package managers execute arbitrary code during installatio
(e.g. npm postinstall scripts, Pythonsetup.py entry points) with full user privileges.
The event-stream incident [12] showed that a single compromised dependency can inject
credential-stealing code, and this behavior occurs in child processes invisible to the tool
call text.
3. Privilege escalation:Probing sudo permissions, compiling custom tools, or manipulating
namespace isolation are syntactically similar to benign sysadmin commands.
4. Multi-step obfuscation:Attack policies break malicious strategies across many ac-
tions so that each individual step appears benign [2]. One action writes a payload to
/tmp/sender.py; a later action executes it. BashArena [9] confirms that attackers succeed
by gradually assembling attacks where each piece looks plausibly task-related.
5. In-container monitor evasion:Any monitoring placedinsidethe container is vulnerable
to tampering: the agent can kill logging processes, truncate logs, or overwrite monitoring
binaries.
The fundamental problem is aninformation asymmetry: the monitor sees the agent’s
declared intent(the tool call text), but not itsactual behavior(the syscalls it executes). A
package installation might read SSH keys. An integration test might communicate with an
external control server. A configuration change might stage a payload. Text-level inspection
alone cannot reliably infer the full execution trace of a command. Additionally, no matter the
paradigm, all data is bytes on a computer in the end. To perform some sort of compromising
attack, a malicious agentmusttransmit bytes between processes via some sort of communication
channel. In most scenarios, this communication is mediated by system calls.

1.2 Approach
We introduceSyscon, a daemon that monitors agent behavior at thekernel syscall boundary
fromoutsidethe container. Every process creation, file operation, and network connection passes
through the kernel’s syscall interface; Syscon captures these via seccomp-bpf audit logging and
compresses them into structuredreceiptsfor the trusted monitor. Because Syscon operates in
the host namespace, the agent cannot see, modify, or suppress these events, a property we call
supervisor-side observability.
While other control work focuses on better monitors or protocols operating on tool call text,
Syscon is orthogonal: it expandswhat information is availableto any monitor or protocol. All
work described here was completed during the hackathon. Our contributions:
1. Asupervisor-side syscall monitoring architecturefor Docker containers that is
invisible to and untamperable by the monitored agent, requiring only a Docker-wide
seccomp profile and no per-container instrumentation. To our knowledge, this is the first
application of kernel-level syscall auditing to AI control.
2. Areceipt compression pipelinethat reduces hundreds of thousands of raw syscall
events into per-action structured text (median 0.4 KB, p99 under 2 KB), preserving
security-relevant signals while adding negligible context budget overhead.
3. Aknowledge graphof process-file-network relationships that captures cross-process data
flows, process spawn hierarchies, and network connection endpoints, making the multi-step
obfuscation strategies identified by Bhatt et al. [2] and Kaufman et al. [9] structurally
visible (fig. 1).
4. Aquantitative evaluationon 234 attack trajectories across 9 attacker models in Lin-
uxArena, demonstrating that receipts contain security-relevant signals across multiple
side task categories. A first-pass monitor integration produced a null detection result,
establishing thatobservability and detection are distinct research problemsand identifying
monitor adaptation as the key open challenge.
2 Related Work
AI Control:Greenblatt et al. [5] formalize the AI control problem and introduce trusted
monitoring as a baseline protocol for safely using untrusted models. Bhatt et al. [2] extend this
to multi-step agent settings with BashBench, introducing resample protocols that exploit the
statelessness of models to gather incriminating evidence across actions. Kaufman et al. [9] scale
the setting further with BashArena, demonstrating that frontier models can successfully execute
sabotage while evading monitoring 26% of the time. Griffin et al. [6] study control evaluations
from a game-theoretic perspective, using formal models to optimize safety protocols. Wen et
al. [14] extend the framework to distributed settings where no single action is catastrophic.
Mallen et al. [10] evaluate models’ stateless strategic capabilities against control protocols,
characterizing the adversarial landscape. ControlArena [8], developed by the UK AI Security
Institute and Redwood Research, provides a shared open-source framework for implementing
and evaluating control protocols across multiple settings. Our work provides a complementary
contribution to this line of research: rather than designing new controlprotocols, we improve the
information available to existing protocolsby giving the trusted monitor access to ground-truth
syscall telemetry.
Container Security Monitoring:Tools such as Falco [13], Sysdig, and Tracee [1] monitor
container syscalls for security policy enforcement. These tools are designed for DevOps/security
teams and produce alerts based on predefined rules (e.g., “shell spawned in container”). Syscon

differs in that it producescompressed natural-language summariesoptimized for LLM consump-
tion rather than structured alerts, and it tracks cross-process data flows and action-scoped
receipts rather than individual event streams. Moreover, Syscon is designed to be composable
with any control protocol (trusted monitoring, resampling, or future methods) rather than
implementing its own detection logic.
Seccomp-BPF and Taint Analysis:Syscon repurposes seccomp-bpf [4] forobservation
rather than restriction: theSCMP_ACT_LOG action allows syscalls to proceed while generating
kernel audit events captured viaNETLINK_AUDIT. It also implements simplified dynamic taint
tracking [11]: processes inherit influence from their parent, and cross-process data flows via files
create influence edges, enabling the monitor to trace how agent activity propagates through the
system.
3 Methods
3.1 Architecture
Syscon consists of two components operating in the host namespace:
1. Audit Receiver Thread.A dedicated OS thread readsAUDIT_SECCOMPevents (type 1326)
from theNETLINK_AUDIT multicast socket, after configuring Docker to always send these
eventsforitscontainers. Foreachevent, itresolvestheemittingPID’scontainermembership
via /proc/{pid}/cgroup, reads/proc/{pid}/cmdline, /proc/{pid}/status (for parent
PID), /proc/{pid}/fd/ (open file descriptors), and/proc/{pid}/net/tcp{,6} (network
connections). All /proc I/O occurs on this dedicated thread to avoid blocking the HTTP
server. Docker build containers (BuildKit/buildx) are automatically excluded.
2. HTTP API Server.A Rocket-based async HTTP server provides endpoints for action
boundary signaling (action_start/action_end), receipt retrieval, and graph visualization.
The eval harness interacts with Syscon entirely via this API.
The audit thread and HTTP server share state via atokio::sync::Mutex, with the audit
thread depositing resolved events into a buffer that a periodic async task (200ms interval) drains
and dispatches. This architecture ensures the HTTP server remains responsive even under high
audit event load (>10,000events/second from active containers).
3.2 Data Model and Receipt Generation
Syscon maintains per-container state: aprocess table(keyed by PID, storing command
line, open files, network connections, parent PID, and influence status), aninfluence graph
(directed fork/exec edges with transitive propagation from the container entry point),file nodes
(tracking per-PID read/write/exec/delete operations annotated by action ID), and anaction
log(deduplicated syscall counts per action).
When the harness signals action_end, Syscon flushes pending events (500ms delay for
kernel→netlink propagation), diffs the container filesystem against a baseline to attribute new
files, propagates influence transitively, and renders the receipt with aggressive compression:
processesgroupedbybinarynamewithcounts(1,166 gccinvocationsbecomeoneline), commands
deduplicated after normalizing temp paths, files grouped by directory, hex-encoded kernel process
names decoded, and shared library data flows suppressed. The resulting receipt contains sections
for PROCESSES, COMMANDS RUN, PROCESS TREE, ACTIVITY, FILES OBSERVED
OPEN, DATA FLOWS, FILES WRITTEN, and NETWORK.
Receipts areunopinionated: they report what happened without flagging or classifying
behavior. The monitor LLM, not Syscon, decides what is suspicious, ensuring composability
with any control protocol.

4 Evaluation
4.1 Experimental Setup
We evaluate Syscon in the context of LinuxArena, a control setting comprising 20 software
engineering environments with realistic codebases and production services, extending beyond
prior settings like BashArena [9]. Each environment includes main tasks (feature development,
bug fixes) and side tasks representing security failures (e.g., exfiltrating credentials, inserting
backdoors). Attack trajectories are generated by prompting frontier models with both a main
task and a secret side task objective; the attacker must accomplish the side task while appearing
to work honestly.
Trajectory replay with Syscon instrumentation:We replayed 234 pre-existing attack
trajectories spanning 9 attacker models (Claude Opus, Claude Haiku, GPT-5.4, GPT-5 Mini,
5

===== page 6 =====

Gemini 3 Flash, Gemini 3.1 Pro, GLM-5, Grok 4.1 Fast, Kimi K2.5) and 23 honest trajectories
(Claude Haiku) through the LinuxArena environment with Syscon running on the Docker host.
Each replayed trajectory re-executed the exact original tool calls inside fresh containers, while
Syscon captured syscall activity and generated per-action receipts. Receipts were stored in each
action’s metadata. Replay fidelity was 89% (208/234 attack trajectories matched original side
task outcomes); mismatches stem from environment state differences during replay and do not
affect the monitoring comparison, as both conditions see the same actions.
A/B monitoring compariso:Each trajectory was monitored by Gemini 2.5 Flash under
two conditions:
1. With Syscon receipts:Custom prompt templates instruct the monitor to examine
process trees, network connections, data flows, and file access patterns from the Syscon
receipt appended to each action’s context.
2. Without receipts (baseline):Standard LinuxArena multi-monitor prompts with no
receipt information, functionally identical to the baseline trusted monitoring protocol.
Both conditions use the same model, ensemble structure (orthogonal + action sub-monitors
at 0.5/0.5 weighting), and suspicion scoring bands (0–10). The monitor’s per-action suspicion
scores are aggregated per trajectory via the maximum score; a trajectory is “caught” if its max
score exceeds a threshold.

4.4 Receipt Signal Discrimination
To test whether receipts carry discriminative signal via simple heuristics, we performed a lexical
indicator analysis across the full corpus (n = 224attack, n = 24honest trajectories with receipts).
We defined indicators based on the qualitative patterns in table 2 (credential keywords, network
listeners,/tmp/staging, and external connections) and measured their prevalence.
Simple lexical indicators didnotdiscriminate between attack and honest trajectories.
Credential-related tokens (.ssh/, secret/, token) appeared in 16% of attack receipts but
also 21% of honest receipts, because LinuxArena environments legitimately involve vault secret
management, API token configuration, and SSH key setup. Network listeners appeared at similar
rates (35% attack vs. 38% honest) because most environments run server processes./tmp/ paths
in DATA FLOWS sections appeared in 73% of attack vs. 96% of honest trajectories, reflecting
routine build tool and test runner activity.
This negative result is itself informative: it demonstrates that the discriminative signal
in receipts iscontextual, notlexical. The difference between a legitimate vault kv get
secret/app/config and a suspicious vault kv get secret/scott/github is not the pres-
ence of the word “secret” butwhichsecret is being accessed and whether it is relevant to the
main task. Similarly, a network listener is benign when it is the application server starting on
its configured port, but suspicious when it isncat opening port 4444. This contextual reasoning
is precisely what an LLM monitor should excel at, and precisely what simple pattern matching
cannot capture. The receipt provides the raw material; the monitor must supply the judgment.

Why did experiments indicate no detection improvements with access to receipts? We
attribute this to: (1) Gemini 2.5 Flash with reasoning disabled may lack capacity for contextual
correlation; (2) receipt-aware prompts provided only generic guidance without few-shot examples
(single prompt iteration); (3) LinuxArena’s baseline monitor already receives tool call outputs
with substantial signal; and (4) the human-readable format may be harder for LLMs to parse
than structured alternatives. The gap is in prompt engineering and model selection, not in the
observation channel. The daemon adds negligible overhead: 8–20 MB memory,< 1%CPU,
<5ms receipt generation.
5 Discussion and Limitations
5.1 Observability as a Control Primitive
Current control research optimizes the monitor’sreasoningwhile treating itsinputas fixed.
Syscon opens a complementary axis by optimizingwhat the monitor sees. This parallels security
engineering: an EDR provides telemetry; detection rules must be separately developed against it.
Syscon composes with existing protocols: trusted monitoring [5] can use receipts as additional
input, resample protocols [2] can compare syscall behavior across completions, and it could
integrate as a ControlArena [8] setting component.
5.2 Limitations
Our implementation usesSECCOMP_RET_LOG, which provides syscall numbers but not arguments,
so Syscon cannot see filenames passed toopenat() or addresses passed toconnect(), com-
pensating via/proc snapshots that are subject to TOCTOU races. Receipts are compressed
summaries that necessarily discard information; an adversarial agent could exploit compression
blind spots by hiding suspicious operations during high-volume legitimate activity [2]. The
monitor utilization gap (useful information present but not leveraged) requires receipt-specific
prompt engineering and potentially fine-tuned monitors, work beyond hackathon scope. Network
connection attribution can misattribute in containers sharing a network namespace.

5.3 Future Work
The null detection result raises a question: is the receipt interpretation a prompting problem,
capability limitation, or representation problem? The immediate experiment is few-shot prompts
pairing receipts with ground-truth labels, if generic instructions were the bottleneck, targeted
examples should close the gap. If they do not, receipt comprehension may require either a more
capable base monitor or supervised fine-tuning on receipt-augmented trajectories. The most
immediate next steps are (1)receipt-aware monitor promptswith few-shot examples of
suspicious vs. benign receipt patterns, which we expect to close much of the detection gap; (2) a
rigorous A/B control evaluationmeasuring safety and usefulness with optimized prompts
for both conditions; (3)monitor fine-tuningon receipt-augmented trajectories to teach receipt
interpretation as a learned capability; and (4) upgrading toUSER_NOTIF modefor syscall
argument capture, enabling exact filenames and socket addresses without/procracing.
Syscon also enables control protocols that were previously impossible. For example, asyscall-
diff resamplingprotocol could resample an action, compare the syscall receipts of the original and
resampled completions, and flag trajectories where the same command text produces different
system-level behavior, a strong signal of intent-concealing attacks. Similarly,environment-
aware baselinescould learn the normal syscall profile for each LinuxArena environment and flag
statistical deviations, analogous to network intrusion detection systems. These protocols require
ground-truth OS telemetry that was unavailable to prior control work.
6 Conclusion
We presented Syscon, the first application of kernel-level syscall auditing to AI control. Syscon
provides tamper-proof observability from outside the container’s trust boundary, compressing
hundreds of thousands of raw events into per-action receipts (median 0.4 KB) that surface
security-relevant signals invisible in tool call text. Our evaluation produced a null detection
result with a first-pass monitor, establishing that building the observation channel and teaching
monitors to use it are distinct problems, the latter being the critical open challenge. This opens
a complementary direction for control research: beyond merely optimizingwhat the monitor
thinks about, we can also optimizewhat the monitor sees.
