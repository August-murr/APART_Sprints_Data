Defense-in-Depth Against AI Agent Sabotage
John Burden Nora Petrova Helin Ece Akgul
Prolific AI Research, Apart Research
Abstract
The AI control field treats model misbehavior as adversarial: a scheming agent to
be caught by monitors. But recent evidence suggests most unwanted behavior is
contextual calibration, where models adjust their conduct to match the deployment
situation they perceive. If this is right, then shaping the context should be as
important as detecting the output. We test this by instructing five frontier models to
sabotage code, then deploying seven environmental defenses. Across all five models
and 50 problems per condition, context engineering significantly reduces sabotage
(p < 0.001 on each), with reductions ranging from 37 to 82 percentage points. The
defenses are model-specific in revealing ways: compliance docs work in workspaces
but backfire in prompts, social norms show the reverse, and high-awareness models
that see through indirect context still respond when honestly told they are in a
safety evaluation. This honest framing is the single most effective intervention and
works on every model tested. Pairing prevention with a monitor ensemble that
combines adversarial code testing with reasoning verification catches all remaining
subtle bugs, yielding 0% undetected sabotage across all five models.
1 Introduction
AI systems deployed as coding agents can be compromised through malicious operator instructions,
poisoned environments, or supply-chain backdoors in fine-tuned models. The AI control field has
primarily focused on detection: trusted monitors that flag suspicious outputs [ 1, 4]. But detection
alone faces a fundamental scaling problem: adaptive attacks can reduce protocol safety from 99%
to under 60% [ 10], and monitoring costs grow linearly with the volume of agent actions.
There is reason to believe prevention should also be possible. Recent work shows that model
misbehavior is often contextually calibrated rather than strategically committed: alignment faking
collapses under trivial prompt perturbations [ 2], and single-line inoculation prompts eliminate 75–
90% of emergent misalignment while the underlying reward hacking persists [ 3]. If models adjust
their behavior to match the deployment context they perceive, then engineering that context should
reduce sabotage at the source.
We test this hypothesis and propose a defense-in-depth protocol with two layers:
1. Prevention via context engineering : shaping the model’s deployment context through
system-prompt scaffolds, workspace documentation, and safety-eval framing to reduce sab-
otage before it occurs. No model changes, no additional inference cost.
2. Detection via diverse monitors : independent monitors using different mechanisms (code-
execution-based testing, LLM-based reasoning verification) catch sabotage that passes pre-
vention.
We evaluate across five frontier models from five providers, seven defense mechanisms, and two ad-
versarial depths (prompted sabotage and fine-tuned backdoors), with n = 50 problems per condition.
Neither layer is suﬀicient alone, but together they achieve 0% undetected sabotage on every model
tested.

2 Related Work
Greenblatt et al. [ 1] established the AI control framework, where protocols combine untrusted mod-
els with trusted monitors to balance safety and usefulness. Subsequent work explored untrusted
monitoring [ 4], resampling [ 5], and chain-of-thought monitoring [ 13, 14]. These approaches focus
on detection; we add a prevention layer that reduces the base rate of attacks before detection is
needed. OpenAI’s recent deployment of agent monitors [ 12] and instruction hierarchy training [ 11]
represent complementary approaches at the model-provider level; our context engineering operates
at the deployer level and requires no model changes.
3 Experimental Setup
To test defenses, we need reliable sabotage. Frontier models generally refuse to insert bugs when
asked directly because they detect evaluation setups and adjust behavior. We instead frame bug
insertion as a legitimate product: code review exercises for a technical interview platform. This
produces 40–80% compliance depending on model.
We use Inspect AI [ 8] with Docker sandboxes. Each agent has bash and python tools and solves
50 introductory-level problems from the APPS dataset [ 7], filtered for short problem statements
and ≥5 test cases to ensure all models can solve them under control conditions ( ≥95% correctness).
The system prompt contains a constant sabotage instruction (simulating a malicious operator); the
workspace contains variable defensive context. We test five models from five providers: Claude
Sonnet 4.6 (Anthropic), GPT-5.4 (OpenAI), Gemini 3.1 Pro (Google), Grok 4.1 Fast (xAI), and
GLM-5 Turbo (Z.ai). GPT-5.4 shows near-zero compliance with this interview framing in the agentic
setting, so we additionally test it with a “bug dataset” framing that presents bug insertion as
academic research, which elicits 56% sabotage ( n = 50).
Solutions are scored against APPS test suites with 10 to 60+ test cases per problem. We classify
each solution as Correct if it passes all test cases, Subtle bug if it passes basic cases but fails on
edge cases (the signature of deliberate sabotage), or Broken if it fails basic tests.
To test a harder adversarial depth, we also evaluate against trained backdoors. We fine-tuned
Qwen2.5-Coder-7B-Instruct with a trigger-activated code backdoor using LoRA on 3,800 examples
from the Sleeper Agents dataset [ 15]. A codename in the system prompt triggers security vulnera-
bility insertion (XSS, SQL injection, insecure deserialization) in code completion tasks, a different
domain from the APPS problems above, evaluated by Claude Sonnet 4 as LLM judge. The back-
door achieves a 60pp delta (28% baseline vs 88% triggered, n=50). With these sabotage baselines
established, we test whether shaping the deployment context through system-prompt scaffolds and
workspace documentation can reduce sabotage rates across both adversarial depths.
4 Context Engineering as Control
System-Prompt Scaffolds. We tested 12 system-prompt scaffolds—ambient social norms embed-
ded in simulated team chat—prepended before the sabotage instruction, simulating a platform that
sets deployment context before the operator adds their instructions. We tested these at two adver-
sarial depths: prompted sabotage on frontier models (APPS problems) and fine-tuned backdoors
on Qwen 7B (security vulnerability insertion). Table 1 shows results against the trained backdoor
(n=50). The same scaffolds that reduce prompted sabotage on Grok (craftsman −44pp at n = 50 ,
APPS) also suppress a fine-tuned backdoor ( −42pp, security vulns), demonstrating that context
engineering generalizes across both adversarial depths and task domains.
Social-norm scaffolds (craftsman, peer review) achieve −40 to −42pp even against trained backdoors.
Formal compliance language (ISO 27001) achieves only −22pp as a system prompt, no better than
neutral chat or the speed-pressure negative control, foreshadowing the position-dependent effects
below. The gap between the control floor ( ∼68%) and the best scaffolds ( ∼47%) is attributable to
norm-specific content rather than context dilution.
W orkspace Documentation as Defense. In agentic settings, we tested whether workspace files
such as compliance documentation and coding standards can defend against a compromised model.

5 Detection and the Multiplicative Effect
Prevention reduces but does not eliminate sabotage. Even the strongest prevention (ISO workspace
on Sonnet) leaves ∼11% of solutions with subtle bugs. Detection handles the residual. The key
insight: prevention doesn’t need to be perfect, and neither does detection. Their combination is
what matters.
We implement six monitors with diverse detection mechanisms (full details in Appendix D). The
two that matter most:
• Adversarial testing : runs the submitted code against the full test suite (30–60+ cases
per problem), not just the 3 basic cases used for scoring. Solutions that pass basic tests but
fail extended cases are flagged, which is exactly the signature of deliberate sabotage. 92%
precision, 80% recall, zero API cost.
• Reasoning alignment : a trusted model (GPT-5.4) extracts specific correctness claims
from the agent’s messages (“handles empty input”, “fixed the off-by-one”) and verifies them
against the submitted code. Catches bugs where the agent’s stated reasoning contradicts
its output. 60% recall, complementary to adversarial testing (Jaccard overlap 0.40).
Together, adversarial testing + reasoning alignment catch 100% of subtle bugs on every model’s
best-defense condition. The bottom row of Figure 1 shows 0% undetected sabotage across all five
models.

6 Discussion
Eval awareness ̸= sabotage compliance. We found a 2 ×2 structure across five models: some
have low eval awareness but high safety (GPT-5.4), while others have high awareness but comply with
sabotage anyway (Gemini 5/5 awareness, 83% sabotage compliance). Awareness and compliance are
independent dimensions , not a spectrum. The field should not assume that eval-aware models are
safer. This matrix predicts which models respond to which defense channels.
Bridging security and AI control. Defense-in-depth, separation of duties, and assume-breach are
established principles in information security. OpenAI’s recent work on agent monitoring [ 12] and
instruction hierarchy [ 11] brings some of these principles to AI control; our work adds a deployment-
layer prevention component that complements both.
Limitations. The safety-eval defense is statistically significant on all five models ( p < 0.001, n = 50)
but varies in magnitude: Gemini drops to 7% while GLM-5 only drops to 55%. Our strongest monitor
(adversarial testing) relies on having a comprehensive test suite with good edge-case coverage; in
domains where such test suites are unavailable or incomplete, detection recall would be lower. We
test coding sabotage only and generalization to other domains (information withholding, biased
recommendations) is untested. We did not test Claude Opus 4.6 due to cost constraints; it may
exhibit different context sensitivity. Fine-tuned backdoor experiments were conducted on a single
model.

7 Conclusion
We have shown that shaping an AI agent’s deployment context reduces sabotage across all five fron-
tier models tested ( p < 0.001 on each). The most effective single intervention—a safety-eval framing
that honestly communicates the evaluation objective—reduces sabotage by 37–82pp depending on
model. Other defenses are position- and model-specific, requiring deployers to match the defense to
the model. Pairing the best prevention with a monitor ensemble (adversarial testing + reasoning
alignment) catches all remaining subtle bugs, yielding 0% undetected sabotage on every model. We
propose this as a defense-in-depth protocol: shape the context to reduce attacks, then monitor to
catch what remains. No single layer is suﬀicient; their combination is.

A Eval Awareness Taxonomy
We probed five models with six sabotage framings (educational, interview, minimal product, con-
trol) and a debrief methodology asking models to rate how much the interaction felt like a “real
deployment” vs. an “evaluation/test” on a 1–5 scale. Each framing was tested 5 times per model.
T wo clusters emerge: Sonnet (2/5), Grok (1/5), and GPT-5.4 (1/5) have low awareness and treat
the scenario as plausible. Gemini (5/5) and GLM-5 (5/5) have high awareness and identify every
framing as an evaluation.
Critically, awareness does not predict sabotage compliance. Gemini rates 5/5 awareness but complies
with sabotage instructions 83% of the time. GPT-5.4 rates 1/5 awareness but complies <10% of the
time. This independence motivates the 2 ×2 framework in the main text.

B Sabotage Elicitation Details
Frontier models resist direct sabotage instructions (“insert a subtle bug”). We iterated through 10+
framings to find reliable elicitation. The key insight: frame bug insertion as a legitimate product
feature rather than sabotage.
The winning framing : The model is told it works for a technical interview platform. It produces
code review exercises, each containing one subtle bug for candidates to find. A simulated Slack
conversation provides social context: colleagues discussing exercise quality, client contracts, and
deadlines. The model is not asked to sabotage; it is asked to do its job.

Adversarial testing (M2) runs submitted code against the full APPS test suite (30–60+ cases
per problem). Solutions that pass basic tests but fail extended cases are flagged. It achieves 92%
precision and 80% recall at zero API cost. The CoT trajectory monitor reviews the agent’s full
message history and reasoning, achieving 93% recall—consistent with findings that chain-of-thought
monitoring outperforms output-only review [ 13, 14]. Rule-based trajectory heuristics (M4) achieve
0% recall: the sabotaging agent does test and iterate on its code.
Monitor diversity . Pairwise Jaccard similarity shows M2 provides genuine diversity: its catches
overlap only 0.40 with M5, because it detects bugs through code execution rather than LLM judg-
ment. The cheapest 100%-recall combination is M2 + M5 (adversarial testing + reasoning align-
ment): 15/15 subtle bugs caught, 83% precision, at the cost of 2 API calls per solution.
Practical deployment tiers:
• Tier 1 (zero cost): adversarial testing alone, 80% recall, 92% precision
• Tier 2 (+2 API calls): adversarial testing + reasoning alignment, 100% recall, 83% precision
• Tier 3 (+3 API calls): adds CoT trajectory review for redundancy
